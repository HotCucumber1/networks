# Документ проектирования RDTP

## 1. Назначение и архитектура

RDTP обеспечивает передачу файла между двумя процессами поверх UDP. UDP не гарантирует доставку, порядок и отсутствие
дубликатов, поэтому эти свойства реализуются на прикладном уровне. Проект разделён на отправитель (`rdt_sender.cpp`),
получатель (`rdt_receiver.cpp`) и общий модуль (`rdtp_common.hpp`). Общий модуль содержит формат пакета, сериализацию,
проверку контрольной суммы, сетевые функции, логирование и симулятор ненадёжного канала. Приложения оформлены классами
`SenderApplication` и `ReceiverApplication`; вспомогательные сущности — `Logger` и `UnreliableChannel`.

Отправитель читает файл в бинарном режиме, делит его на блоки по 1024 байта и присваивает каждому блоку возрастающий
номер. Получатель проверяет пакет, восстанавливает правильный порядок данных и записывает их в выходной файл. После
приёма всех блоков отправитель посылает FIN, получатель отвечает FIN-ACK.

## 2. Формат пакета

Заголовок передаётся в сетевом порядке байтов и упакован без дополнительного выравнивания. Он содержит:

| Поле          |       Размер | Назначение                                      |
|---------------|-------------:|-------------------------------------------------|
| rdtpName      |      4 байта | Сигнатура RDTP                                  |
| version       |      2 байта | Версия формата                                  |
| type          |       1 байт | DATA, ACK, FIN или FIN-ACK                      |
| reserved      |       1 байт | Резерв                                          |
| transferId    |      4 байта | Идентификатор передачи                          |
| sequence      |      4 байта | Номер DATA или подтверждаемая позиция           |
| totalPackets  |      4 байта | Общее число блоков                              |
| payloadLength |      2 байта | Длина полезной нагрузки                         |
| reserved2     |      2 байта | Резерв                                          |
| checksum      |      4 байта | FNV-1a по всему пакету с нулевым полем checksum |
| payload       | 0–1024 байта | Данные файла                                    |

Пакет отвергается, если сигнатура/версия неверны, длина не совпадает с фактическим размером датаграммы, полезная
нагрузка превышает лимит или контрольная сумма не совпадает. Поля целых чисел преобразуются функциями `htonl`, `htons`,
`ntohl`, `ntohs`.

Типы пакетов:

- DATA — фрагмент файла.
- ACK — подтверждение приёма. Для GBN это кумулятивный номер последнего непрерывно принятого пакета; для SR — номер
  конкретного пакета.
- FIN — уведомление об окончании передачи.
- FIN-ACK — подтверждение завершения.

## 3. Конечные автоматы

### Отправитель

1. Подготовка: открыть файл, вычислить число блоков, создать UDP-сокет.
2. Передача: отправлять DATA, пока `nextSequence` не достигнет `base + window`.
3. Ожидание ACK: принимать подтверждения через `select()` с коротким интервалом ожидания.
4. Продвижение окна: при ACK сдвигать `base`; SR сдвигает базу через непрерывно подтверждённые сегменты.
5. Тайм-аут: повторно отправить потерянные сегменты согласно выбранному алгоритму, уменьшить окно перегрузки и увеличить
   RTO.
6. Завершение: когда подтверждены все сегменты, повторять FIN до получения FIN-ACK или исчерпания числа попыток.

### Получатель

1. Ожидание DATA.
2. Проверка идентификатора передачи, длины и контрольной суммы выполняется общей функцией десериализации.
3. GBN принимает только ожидаемый номер и отправляет кумулятивный ACK. Дубликат вызывает повтор ACK, но повторно не
   записывается.
4. SR принимает пакеты в окне приёма, буферизует пришедшие не по порядку и сбрасывает непрерывную последовательность в
   файл.
5. При FIN и полном наборе блоков получатель сбрасывает буфер файла и отправляет FIN-ACK.

## 4. Go-Back-N и Selective Repeat

В GBN получатель не буферизует сегменты, пришедшие за пропущенным номером. Если потерян сегмент N, последующие сегменты
до восстановления N не продвигают непрерывную позицию. Отправитель по тайм-ауту базового сегмента повторяет всё
неподтверждённое окно. Это просто, но при потерях создаёт избыточные передачи.

В SR получатель сохраняет сегменты, пришедшие не по порядку, и подтверждает каждый сегмент отдельно. Отправитель
повторяет только сегменты без ACK по истечении их тайм-аутов. Это уменьшает повторную передачу при независимых потерях,
но требует буферизации и индивидуального состояния каждого сегмента.

## 5. Управление окном и тайм-аутом

Максимальное окно задаётся параметром `-window`. Адаптивное окно начинается с одного сегмента. При успешных
подтверждениях в фазе slow start оно увеличивается быстрее; после достижения порога `ssthresh` используется аддитивное
увеличение. При тайм-ауте `ssthresh` уменьшается примерно вдвое, окно сбрасывается до одного сегмента. Параметр
`-no-adaptive` оставляет окно фиксированным на уровне максимального значения.

RTT оценивается по времени между отправкой и ACK. Для SR образцы от повторно переданных сегментов не используются. RTO
рассчитывается на основе сглаженного RTT и вариации RTT, ограничивается диапазоном 100–5000 мс и увеличивается при
тайм-ауте.

## 6. Обработка ошибок и ресурсов

Потери DATA и ACK имитируются случайно. Задержка и джиттер настраиваются параметрами командной строки. Дубликаты не
должны повторно попадать в файл. Неверные или повреждённые пакеты не подтверждаются. Сокеты закрываются при штатном
завершении и основных ошибках запуска; файлы закрываются средствами RAII и явно перед завершением. Временные ожидания
выполняются через `select()`.
