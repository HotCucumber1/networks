# Алгоритм кэширования HTTP Web Proxy

## Назначение

Кэш уменьшает число обращений к исходным веб-серверам и ускоряет повторное получение одинаковых HTTP-объектов. Кэш хранится на диске, поэтому его содержимое сохраняется после перезапуска прокси.

## Формирование ключа

Ключ объекта строится из имени хоста, порта и пути запроса: `host:port/path`. Из ключа вычисляется 64-битный FNV-1a хеш. Хеш используется как имя файла, чтобы не создавать вложенные каталоги для URL и не допускать попадания специальных символов URL в имя файла. Для каждого объекта используются два файла: `.cache` с полным HTTP-ответом и `.meta` со временем окончания свежести в Unix time.

## Обработка GET

1. Прокси разбирает запрос и формирует ключ.
2. CacheManager ищет файл объекта и метаданные.
3. Если объект существует и срок свежести не истёк, прокси возвращает сохранённый HTTP-ответ клиенту. Это CACHE HIT.
4. Если объекта нет, фиксируется CACHE MISS. Если объект есть, но устарел, выполняется повторная проверка.
5. При промахе прокси подключается к исходному серверу и пересылает GET.
6. Ответ передаётся клиенту. Кэшированию подлежат только ответы со статусом 200.

## Политика хранения

Ответы с Set-Cookie, Vary, Cache-Control: private и Cache-Control: no-store не сохраняются. Запросы с Cookie или Authorization обходят кэш, чтобы персонализированные данные не попали в общий кэш. Значение max-age задаёт срок свежести; максимальный срок ограничен 24 часами. Если max-age отсутствует, используется срок по умолчанию 60 секунд. Для no-cache объект может быть сохранён, но считается требующим проверки перед повторным использованием. Ошибки 404 и другие статусы, отличные от 200, не сохраняются.

Файл сначала записывается во временный файл, после чего переименовывается в конечное имя. Это снижает риск оставить частично записанный объект при одновременном доступе или аварийном завершении процесса. Операции CacheManager защищены mutex.

## Валидация устаревшего объекта

Если сохранённый объект устарел, прокси использует ETag в заголовке If-None-Match и/или Last-Modified в If-Modified-Since. Если сервер отвечает 304 Not Modified, сохранённое тело остаётся действительным, срок свежести обновляется, а клиенту возвращается сохранённый ответ. Если сервер возвращает новый 200, новый ответ передаётся клиенту и заменяет кэшируемый объект.

## POST

POST не кэшируется, поскольку результат может зависеть от тела запроса и изменять состояние сервера. Прокси читает Content-Length байтов тела, передаёт тело исходному серверу и возвращает его ответ клиенту.

## Параллельная работа

Принятые соединения помещаются в ограниченную очередь ThreadPool. Рабочие потоки обрабатывают клиентов независимо. Доступ к файлам кэша синхронизирован внутри CacheManager; счётчики статистики используют атомарные переменные. При переполнении очереди клиент получает 503 Service Unavailable.
